# YOW Deferred QA Plan

This is the single deferred QA plan for Your Own World.

Use this file when QA is intentionally postponed so development can continue. Every new implementation that creates, changes, or retires behavior must add its required verification here in the same turn. Keep `docs/ROADMAP.md` as the planning source of truth for scope and status; use this file for the accumulated checks that need to be run before public paid/final launch.

## Operating Rules

- Do not treat an item as launch-ready just because it is implemented.
- Add QA items here when roadmap rows say "needs QA", "needs browser QA", "needs urgent QA", or when new implementation changes a user workflow.
- Keep items written as concrete checks that can be performed later.
- Mark checks as `Deferred` until they are actually run.
- When a check passes or fails, update both this plan and the relevant roadmap row or bug entry.

- 🐛 Partial (2026-09-01, branch `fix/ai-proxy-authz`, audit finding P0-02): `api/ai-proxy.js` now requires a valid Supabase session (`Authorization: Bearer` verified via `supabase.auth.getUser`), rejects Free-plan users server-side (403) via a new `hasAiEntitlement()` check, enforces a durable per-user rate limit backed by a new `ai_proxy_requests` table (`supabase/migrations/20260901_ai_proxy_rate_limits.sql`, RLS-locked to the service role, default 30 requests/10 min, configurable via `AI_PROXY_RATE_LIMIT_MAX`/`AI_PROXY_RATE_LIMIT_WINDOW_MINUTES`), clamps `maxTokens` to a ceiling of 8192 regardless of what's requested, and restricts `Access-Control-Allow-Origin` to an explicit allowlist (`SITE_URL`, local dev ports, Tauri desktop origins, the current deployment's own `VERCEL_URL` so Vercel preview deployments still work) instead of reflecting any caller-supplied `Origin`.

  **Security review caught and this branch fixed a real bypass in its own first draft, not a pre-existing issue**: the entitlement check initially reused the shared `getMembership()` helper directly, which falls back from `app_metadata` (service-role-only, written only by the Stripe webhook) to `user_metadata` — a field any signed-in user can write themselves via `supabase.auth.updateUser()`. Every genuinely Free user has no `app_metadata` subscription fields at all, so that fallback was live for exactly the population the 403 gate exists to reject: a brand-new free signup could self-grant AI access with one browser-console call, fully defeating the check. Fixed by adding `hasAiEntitlement()`, which calls `getMembership()` with `user_metadata` stripped out — reusing its tested plan/trial logic while trusting only server-controlled fields (`app_metadata` + `created_at`, never client-writable). This is now the one hardened exception to `getMembership()`'s general "read app_metadata, fall back to user_metadata" pattern used everywhere else in the app for UI/display purposes — audit finding P0-01 (separate, broader, also fixed — see [PR #41](https://github.com/bishop7124-ctrl/YoW/pull/41)) covers making entitlement trustworthy everywhere else that pattern appears.

  Unit-tested (`tests/api/ai-proxy.test.js`, 18 cases: no token, invalid token, Free user rejected before any provider call — including a dedicated regression test for a tampered `user_metadata` claim of a paid plan, and confirmation a genuinely new user still gets their trial window from `created_at` — rate limit allow/deny, rate-limit-infra-error fails open, CORS allowlist/reject/Vercel-preview-origin, `clampMaxTokens` bounds) — full suite 468/468, lint clean (0 errors, 97 pre-existing warnings unrelated to this change).

  **Known limitation, genuinely out of scope for this branch:** the rate limiter's check-then-insert is not atomic (documented in code) — a tight concurrent burst from one user could exceed the cap by roughly the number of in-flight requests; acceptable tradeoff for a simple durable implementation, revisit with a Postgres RPC if real abuse patterns show it matters.

- 🐛 Partial (2026-09-01, branch `fix/email-endpoint-authz`, audit finding P0-03): code-side fixes for all five flagged endpoints —

  - `supabase/functions/send-reset-email`: `redirectTo` is now validated against an explicit origin allowlist (was previously accepted as-is, a real open-redirect risk in a real Supabase recovery link — a link that, if the legitimate user's own click got redirected to an attacker domain, could carry their session token with it) — bad/missing values silently fall back to the safe default rather than failing the request. Added a durable per-email rate limit (new `email_action_rate_limits` table, `supabase/migrations/20260901120000_email_action_rate_limits.sql`, default 5 requests/15 min). No longer logs the Resend key prefix.

Security review caught one more thing: the signature originally covered only the bare user id with no purpose/scope separator (not exploitable today — no other endpoint reuses this secret/shape — but would have been replayable against any future action that did); fixed to sign a scoped `reengagement-unsubscribe:<userId>` string on both sides.
